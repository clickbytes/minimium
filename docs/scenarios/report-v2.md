# Load-test report schema v2

The load-test executable prints one JSON object per run with
`schema_version: 2`. The text format carries the same run, generator, CPU, and
server metadata as key/value fields; absent optional values appear as `n/a`.
No benchmark result is recorded here.

## Top-level fields

The report preserves the prior generator result fields:

- `scenario`, `os`, `arch`
- `clients_requested`, `clients_connected`, `workers`, `elapsed_seconds`
- `pongs`, `errors`, `rate_limited`, `timeouts`, `pongs_per_second`
- `moves_sent`, `moves_per_second`, `shots_sent`, `shots_per_second`,
  `shots_hit`, `kills`
- `chat_sent`, `chat_received`, `chat_sent_per_second`
- `snapshots_received`, `snapshots_per_second`
- `application_bytes_sent`, `application_bytes_received`
- `handshake_failures`, `disconnects_before_start`, `clients_connected_at_start`,
  `disconnects_during_measurement`, `clients_connected_at_end`
- `setup_application_bytes_sent`, `setup_application_bytes_received`,
  `measurement_application_bytes_sent`, `measurement_application_bytes_received`
- `client_measurements`: up to 10,000 records sorted by numeric generator ID,
  with successful measurement-window application bytes sent and received and
  `connected`/`disconnected` status. Setup failures have zero measurement bytes.
  `connected` means no disconnect was observed before the window ended; it is
  not proof that the socket was still live after the last observation. No
  profile identifier or administrative token is included. A nonblocking socket
  operation begun just before the deadline may complete just after it; its
  returned bytes are attributed to the measurement window.
- `rtt_samples`, `rtt_min_ms`, `rtt_avg_ms`, `rtt_p95_ms`, `rtt_p99_ms`,
  `rtt_max_ms`

Their values come from the simulated generator's `WorkerStats`, elapsed wall
time, or Rust's OS and architecture constants. RTT percentiles are estimates
from the generator's fixed histogram buckets. Existing `application_bytes_*`
fields remain total application bytes for the complete run, including setup.
The new setup and measurement byte fields split those totals at the shared
measurement start.

Additional run metadata fields are `run_id`, `rustc`, `build_profile`,
`scenario_id`, `cpu_label`, and `cpu_mhz`. The run ID is generated by the
process; Rust version and profile come from the build script and Cargo's
`PROFILE`; scenario ID comes from the explicit scenario ID option or the
scenario name. CPU label and MHz are optional user-supplied machine details.
Unavailable optional CPU values are JSON `null`.

## Generator and server objects

`generator` records the requested `address`, `requested_seconds`, and
`thread_mode` separately from `workers_actual`; it also repeats requested and
connected client counts. `workers` remains at the top level for compatibility
and has the same actual worker count.

`server.before`, `server.measurement_start`, and `server.after` each contain
`status` and `metrics` strings captured with authenticated admin `status` and
`metrics show` requests. `before` is captured before client setup;
`measurement_start` is captured after all successful Welcome and SetName
acknowledgements, immediately before the shared workload start; `after` is
captured after all workers finish. These are the server's returned text, not
generator estimates.
If a sample is unavailable, the corresponding object is JSON `null`. A sample
is rejected if the endpoint identity changes between its two requests. The
endpoint token and data directory are never serialized.

`clients_connected` counts clients that received Welcome. A client is
`clients_connected_at_start` only if it also received the SetName acknowledgement
and remained connected through the setup drain. `handshake_failures` counts
connections that failed to complete the connection, Welcome, or SetName
acknowledgement steps. `disconnects_before_start` counts clients that completed
Welcome and SetName but were observed disconnecting before the shared workload
start. `disconnects_during_measurement`
counts clients observed disconnecting during the workload window;
`clients_connected_at_end` counts start clients not observed disconnected by
the end of that window. Connected-at-start is the last observed live population
during setup and the pre-start drain, not a guarantee that every socket was
alive at one exact instant. Workers monitor their sockets while other clients
finish setup and through the shared-start boundary. These counters let the reader
reject runs that did not maintain the requested population.

The shared measurement window starts after all workers report setup readiness,
the optional server `measurement_start` sample, and a short common start delay.
Movement, combat, ping, and chat schedules are anchored to that same monotonic
instant. Setup traffic is counted separately; workload rates use the elapsed
time from that common start. Server status and metric strings describe the
actual server process; compare `measurement_start` and `after` for interval
counters, and use `before` to inspect setup effects. Manifests record intended
server lanes, player cap, map, ports, and data directories separately from
generator settings.
