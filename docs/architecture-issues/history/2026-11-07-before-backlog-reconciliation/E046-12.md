# E046-12 — Dokończyć SettingsStore i rzeczywiste wydzielenie aplikacji

## Powiązania GitHub

Epic nadrzędny: https://github.com/clickbytes/minimium/issues/347

Zależności do zakończenia źródłowego: [E046-11](https://github.com/clickbytes/minimium/issues/358).


Priorytet P1. Kroki 38–39. Właściciel: apps/client. Zależność: E046-11.

Potwierdzone w `apps/client/src/application.rs`: SettingsStore przechowuje stringowe startup/requested/overrides/sources, lecz nie ma efektywnej wartości/powodu różnicy. ClientApplication odwołuje się do `crate::renderer::client_game::ClientGameState`. WorldTransitionController zawiera HashMap i bool-e zamiast jawnej maszyny stanów.

Gdzie dodatkowo: `renderer.rs`, `renderer/{settings,quality,client_game,controller,session}.rs`, `renderer/session/`, `client_commands/`, `terminal_client/`, `config.rs`.

Do wykonania: przenieść stan i zachowanie sesji/świata poza moduł renderer. Wprowadzić kontrolowane przejścia przygotowanie→gotowość→commit/anulowanie/błąd i usunąć kombinacje flag dopuszczające sprzeczności. Renderer dostaje widok prezentacji. Ustalenie effective/requested/source/reason musi być wspólne dla get/set/reset/show/save, locale i bindings; runtime/server settings nie stają się preferencjami GPU. Zweryfikować reset do rzeczywistej warstwy startowej. Wspólne frontendowe komendy nie mogą wymagać GPU. Nie przenosić całego Renderer do nowego pliku pod inną nazwą.

Akceptacja: operacje connect/transfer/set można wykonać przez właściciela aplikacji bez dostępu do GpuResources; terminal kompiluje się bez desktop; każdy stan przejściowy ma jedną legalną ścieżkę zakończenia; wartości efektywne mają jawny powód różnicy.

## Instrukcja wykonania krok po kroku

1. Podziel application.rs według odpowiedzialności: proponowane nowe moduły application/settings.rs, application/transitions.rs, application/game.rs i application/ui.rs. Są to docelowe lokalizacje, nie twierdzenie, że już istnieją. Przenieś ClientGameState z renderer/client_game.rs wraz z użyciem w obu frontendach; zachowaj GPU-only dane w renderer.

2. W SettingsStore wprowadź rekord wartości requested, source i wyniku zastosowania effective/reason. Dla locale i bindings użyj walidowanych typów; serializacja config może pozostać tekstowa na granicy. Nie utrzymuj niezależnych mutowalnych kopii requested w renderer.

3. Przestaw get/set/reset/config show/config save na ten sam rekord. Set najpierw parsuje i waliduje, potem aktualizuje requested i uruchamia konsumenta; wynik zastosowania aktualizuje effective/reason. Reset bierze resolved startup, a save zapisuje trwałe preferencje requested, nie chwilowe fallbacki urządzenia.

4. Zdefiniuj enum faz transferu z context/ticket i danymi potrzebnymi danej fazie. Metody przyjmują zdarzenie i zwracają efekty, zamiast pozwalać obcym modułom ustawiać bool-e. Opisz legalne przejścia prepare/ready/commit/fail/cancel i odrzucanie starego ticketu.

5. Przenieś kontrolę connect/disconnect/world catalog/transfer/loading z renderer/session i controller do ClientApplication. Efekty wymagające GPU wyrażaj jako żądania przygotowania/zwolnienia, a wynik GPU wraca jako zdarzenie do kontrolera; nie przekazuj &mut GpuResources aplikacji.

6. Overview otrzymuje metody wejścia/wyjścia i własny model zamiast zewnętrznych zapisów do luźnych flag. Renderer dostaje read-only presentation view. Console command executor desktop/terminal odwołuje się do wspólnego application/runtime API.

7. Usuń stare pola, wrappery i pub(crate) umożliwiające obejście właścicieli. Wyszukaj application→renderer::client_game i ręczne *_base/*_override; nie może pozostać produkcyjny caller. Zaktualizuj README i architekturę, zachowując cfg dla terminal-only.
