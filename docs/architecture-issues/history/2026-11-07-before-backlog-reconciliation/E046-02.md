Priorytet P1. Kroki 04–08. Właściciele: platform, diagnostics, telemetry, adaptery i entrypointy. Zależność: E046-01.

Gdzie: `crates/platform/src/app_paths.rs`, `startup_status.rs`, `crates/diagnostics/`, `crates/telemetry/src/logging/`, `apps/{client,server,ctl,loadtest}/src`, `crates/client-runtime/src/bootstrap/`, błędy w asset-io, storage i runtime’ach.

Zakres:

- Prześledzić pojedyncze rozstrzygnięcie ścieżek i przejście absolutnych danych/logów do dziecka. Wykluczyć ponowny odczyt środowiska w runtime. Zweryfikować `--log-dir` i domyślne ./logs.
- Prześledzić rekord 8 KiB/32 pól wraz z narzutem serializacji, `truncated`, kontrolowanym rejestrem domen oraz brakiem nieograniczonej alokacji przed obcięciem.
- Sprawdzić UTC dnia uruchomienia, atomową rezerwację numeru, parent_run_id, osobne kolejki 4096/128, nieblokujące emit, podsumowanie strat i propagację awarii writera.
- Udowodnić rotację 16 MiB + dwa segmenty oraz retencję 7 dni/2 GiB tylko własnych zakończonych uruchomień chronionych rzeczywistą blokadą.
- Dla wszystkich domen z planu wskazać podłączony logger. Oddzielić stdout CLI od diagnostyki. Prześledzić brak credentiali i pełnego czatu w polach.
- Startup musi weryfikować attempt ID i stan starting/ready/failed; stderr pozostaje ograniczonym fallbackiem awarii przed publikacją statusu.
- Prześledzić source i stabilne kategorie błędów aż do UI/logowania; nie usuwać semantyki na pośrednim `.to_string()`, `.ok()` czy ignorowanym Result.

Akceptacja: każdy limit i procesowy konsument ma konkretny dowód; błędy writera i statusu docierają do właściciela; żadna domena nie wykonuje zapisu logu. Brak dowodu staje się poprawką w tym issue, nie deklaracją sukcesu.

## Instrukcja wykonania krok po kroku

1. Zacznij od AppPaths i entrypointów czterech aplikacji. Narysuj przepływ: argument/config/environment → AppPaths → konfiguracja runtime → proces potomny. Znajdź odczyty std::env/current_dir w runtime i adapterach; przenieś rozstrzyganie domyślnych ścieżek do entrypointu i przekaż PathBuf. Zachowaj jawne użycie adapterów OS niezwiązane z ponownym wyborem konfiguracji.

2. W diagnostics odczytaj konstruktory DiagnosticEvent/DiagnosticField i emit sinka. Wyznacz rzeczywisty maksymalny rozmiar po escapowaniu JSON. Jeżeli limit obejmuje tylko surowe stringi, ogranicz także rekord zakodowany; zostaw miejsce na truncated i pola obowiązkowe. Zatrzymaj alokację przy limicie, zamiast najpierw formatować dowolnie długi komunikat.

3. W telemetry/logging prześledź inicjalizację katalogu, atomowe create_dir przy kolizji, lock aktywności oraz zapamiętany dzień UTC. Sprawdź, że kolejne rekordy nie wybierają nowej daty po północy; parent_run_id musi pochodzić z launch configuration rodzica.

4. Dla emit rozpisz osobno zwykłą kolejkę 4096 oraz rezerwę warn/error 128. Zastąp blokujące enqueue try_send lub równoważną ograniczoną operacją; przy pełności zwiększ licznik strat i po odzyskaniu miejsca wyemituj bounded summary przez writer. Sprawdź, że sam summary nie zapętla logowania.

5. W writerze sprawdź progi rotacji i usuwanie wyłącznie własnych zakończonych runów. Każde usunięcie poprzedź przejęciem blokady i walidacją ścieżki pod log root; sam PID nie uprawnia do usunięcia. Błąd open/write/flush musi zostać zachowany do odbioru przez aplikację.

6. W startup_status i bootstrap sprawdź tworzenie unikalnego attempt ID przez klienta, przekazanie go serwerowi, atomowy zapis starting/ready/failed oraz porównanie przy odczycie. Usuń decyzje o sukcesie oparte na tekście stderr; zachowaj tylko ograniczony ogon diagnostyczny przy braku statusu.

7. Dla każdej domeny z pierwotnego kroku 07 znajdź tworzenie loggera i co najmniej właściwą granicę operacji. Przejrzyj payloady auth/admin/chat i usuń credentiale, tokeny oraz pełny czat z diagnostyki. Pozostaw odpowiedzi CLI na stdout.

8. W asset-io/procgen/storage/session/server/commands prześledź reprezentatywny błąd każdej wymaganej kategorii od źródła do aplikacji. Zmień pośrednie String na lokalny enum/source tam, gdzie wyższa warstwa musi rozróżnić przyczynę; UI mapuje kod dopiero na końcu. Sporządź tabelę kod→wariant→źródło→konsument.

## Wynik i dowody

`docs/architecture-execution.md` E046-02 source evidence zawiera ślad argument/config/environment → `AppPaths` → runtime/process child, w tym client/server/ctl/loadtest. Runtime otrzymuje resolved `PathBuf`; jedyne runtime environment mapowanie pochodzi z application. `DiagnosticEvent::field` ogranicza surowe pola, a `RunWriter::write_record` mierzy escaped JSON przed złożeniem rekordu. `RunDirectory` zapamiętuje UTC start day i atomowo rezerwuje run ID; `QueueSink::emit` używa `try_send` do kanałów 4096/128 i writer składa bounded loss summary. `RunWriter::rotate` utrzymuje dwa segmenty; `cleanup_completed_runs` usuwa wyłącznie zakończone runy pod log-root po przejęciu aktywnego locka. Tabela domen i błędów znajduje się w wierszach 57–71 tej sekcji: wskazuje composition owner, źródłowy wariant błędu i końcowego consumer’a.

Startup status wiąże attempt ID z `Starting`/`Ready`/`Failed` oraz oczekiwanym endpoint; stderr jest ograniczonym fallbackiem przed publikacją statusu. Błędy writera zachowują `io::Error`, a typowane błędy domen dochodzą do application/UI mapping. Credentiale i pełny czat nie są logowane; CLI pozostaje stdout. README właścicieli diagnostics/telemetry/platform i client/server-runtime opisują kontrakty.

Kod/review źródłowe: complete. Locked builds E046-17: passed. Rotacja, presja kolejek, północ podczas procesu i błędy procesów pozostają runtime-unverified.
