1. W gameplay znajdź GameplaySystemContext i definicje modułów/systemów; w runtime/schedule odczytaj wszystkie run_stage callsite’y. Dodaj read-only simulation_tick do publicznego kontraktu i przekaż rzeczywisty tick z schedulera serwera, także dla Environment/PostSimulation.

2. Zastąp globalne startup_ran stanem wykonania powiązanym z cyklem świata. Przekaż systemom jawny kontekst świata oraz informację New/Restored; Startup wykonuje się raz po przygotowaniu tego świata. Nie dodawaj mechanizmu dynamicznego tworzenia światów, jeśli go nie ma; obejmij istniejące ścieżki instalacji.

## Wynik i dowody

`GameplaySystemContext` przekazuje scheduler tick, world ID/lifecycle state i neutralne API staged effects; `ModuleRegistry::ordered_systems` sortuje deterministycznie i odrzuca duplicate/missing/cycle dependencies. `run_stage` wywołuje system per world i stage; Startup dostaje `New/Restored`, marker zapisuje się dopiero po udanym batch. `WorldEffectBuffer` waliduje do 256 operacji oraz 1 MiB payload, sprawdza component schema/permissions/references/reservations/transfer placement przed atomic commit; błąd odrzuca całą stage. Sample portal rejestruje schema/decoder, tworzy wyłącznie przy New, a PostSimulation obsługuje `InteractEntity`, sprawdza portal schema, pozycję/dystans i emituje `RequestTransfer`; server owner zachowuje readiness/placement/commit. Desktop i terminal wybierają portal przez replica entity. Usunięto `UsePortal`, `WorldDefinition.portal`, global command `OnceLock` i infra-coupled sample behavior.

Public API i real consumer są opisani w `crates/gameplay/README.md` i `games/sample/README.md`; szczegóły tick/startup/effects i lifecycle są w execution rows 27–29. Builds E046-17 passed. Startup ordering/portal flow nieuruchomione runtime.
