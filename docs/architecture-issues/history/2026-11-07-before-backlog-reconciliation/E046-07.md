## Wynik i dowody trwałości encji

`EntityStore` rejestruje ścisłe schematy i ogranicza entity/component counts/bytes; spawn/upsert/remove/despawn produkują monotoniczny journal. `WorldEffectBuffer` i `SnapshotBudget` budują kandydackie store/journal/budget przed commit, więc błąd elementu batcha nie publikuje wcześniejszych zmian. Stare component-object wrappers, origin map i loaded-state rehydrate zostały usunięte.

`RuntimeServerConfig`/`ServerRuntime::run_with_config` rejestruje sample moduły i schematy przed `PlayerStore::load`. Loader składa wszystko do staged state, weryfikuje duplicate IDs, referencje, component schemas, licznik ID i wspólny 4 MiB raw payload przed publikacją. Zapis format 10 przechodzi przez wspólny counting/stream encoder z limitem 128 MiB; wcześniejszy/nieznany version odrzucany jest w header gate zanim persistence worker albo replacement snapshot powstaną.

Snapshot producer table: autosave `WorldRegistry::snapshot_for_save` kopiuje aktualny entity set (w tym pustą encję), counters i `content_initialized`; shutdown używa tej samej capture, a final revision nie może być zastąpiona autosave. Startup per-world `New/Restored` emituje portal template tylko dla New, a znacznik inicjalizacji commits razem z batch. Źródłowy cykl: nowy świat → Startup emituje portal → save zapisuje portal/ID/marker → load odtwarza → despawn usuwa portal i journaluje remove → kolejny save/load zachowuje brak portalu oraz marker=true i nie dosiewa go. Encja bez komponentów pozostaje zapisana; storage budget jest rezerwowany/zwalniany w mutation batch.

Integracja E046-09: entity journal/full/delta buduje się z tego samego żywego `EntityStore`; replica ack następuje po commit. Integracja E046-10: final shutdown capture jest obowiązkowy, final save error/timeout wpływa na wynik procesu, stary atomowy plik pozostaje chroniony przez staged replacement. To zamyka source review kroku 26; runtime restart/failure nie zostały wykonane.
