# E046-05 — Zweryfikować autoryzację każdego wejścia mutującego

## Kolejność i punkt wejścia

Pozycja 5/18. Rozpocznij dopiero po zamknięciu [E046-04](https://github.com/clickbytes/minimium/issues/351) i wszystkich wcześniejszych issues. Następne: [E046-06](https://github.com/clickbytes/minimium/issues/353).

Pracujemy nad jednym issue naraz. Najpierw porównaj poniższe wymagania z bieżącym drzewem, potem wykonaj brakujące poprawki i przegląd źródłowy. Zachowaj poprawne istniejące rozwiązania. Dawne opisy usterek i raporty Complete nie są dowodem obecnego stanu. Ścieżki w instrukcji są punktami wejścia; po przenosinach znajdź aktualnego właściciela.

Zakończ kompletną macierzą każdej mutującej wiadomości: handler → admission → kontekst → Principal → permission → pierwsza mutacja. Uwzględnij desktop, terminal, loadtest i lokalny launcher --dev.

Zależności do zakończenia źródłowego: [E046-04](https://github.com/clickbytes/minimium/issues/351).


Priorytet P0. Kroki 17–20. Właściciele: core, protocol, server-runtime i kompozycja aplikacji. Zależność: E046-04.

Gdzie: `apps/server/src/developer_auth.rs`, `crates/server-runtime/src/authentication.rs`, `runtime/admission/`, `crates/core/src/identity.rs`, `crates/protocol/src`, `crates/simulation/src/simulation/`, launchery i konfiguracja serwera.

Zakres: sporządzić macierz wiadomość → stan admission → permission → mutacja. Potwierdzić nieblokujące begin/poll/cancel, 10 s, jedną próbę/połączenie, Principal przed profilem i wykluczenie aktywnego profilu. Zwykły klient ma tylko gameplay; dev jawnie z --dev, także lokalny host i launchery. Lot, polityka ruchu, teleport i czas muszą być autoryzowane przed mutacją. Kanał admin zachowuje ochronę zapisu/stop. Wire ma jedną wersję 18, kontekst świata i payload <=4096. MovementIntent nie zawiera autorytatywnej prędkości/prawa do lotu; finiteness, osie i długość są walidowane, polityka serwerowa ma rewizję.

Akceptacja: kompletna macierz obejmuje desktop, terminal i loadtest; żadna mutacja nie zależy od ukrycia przycisku. Provider developerski pozostaje jawnie niezabezpieczoną deklaracją profilu, bez kont/TLS.

## Instrukcja wykonania krok po kroku

1. W protocol/models i dispatch wypisz wszystkie wiadomości klienta zdolne zmienić stan. Dla każdej wskaż handler admission, dozwolony stan sesji, permission i pierwszą mutację; tabela jest obowiązkowym wynikiem.

2. W authentication oraz admission/identity prześledź start próby, deadline 10 s, odbiór Principal i cancel przy disconnect. Zablokuj drugą próbę i aktywację profilu przed wynikiem providera; zachowaj kontrolę już aktywnego profilu.

3. W developer_auth skontroluj oba zestawy permissions: normalny tylko gameplay, dev rozszerzony. Przeprowadź flagę --dev przez parser, config, launchery i owned server; nie wyprowadzaj uprawnień z samego provider ID lub credential payloadu.

4. W każdej mutacji z tabeli umieść sprawdzenie kontekstu, danych i permission przed enqueue/mutation. Dotyczy polityki ruchu, lotu, teleportacji i czasu; log odmowy zawiera kod akcji i connection ID bez sekretów.

5. W MovementIntent/MovementPolicy i kodeku usuń możliwość przesyłania autorytatywnej prędkości/akceleracji/prawa do lotu jako zwykłego ruchu. Handler składa intencję z polityką serwera; osobna dev operacja zwiększa rewizję polityki i odsyła ją do predykcji.

6. Przejrzyj konstrukcję wiadomości desktop, terminal i loadtest oraz decoder/encoder. Usuń stare bezkontekstowe reprezentacje, decoder v17 i payloady >4096. Aktualizuj istniejące testowe callsite’y tylko mechanicznie.

7. Dla każdej pozycji tabeli opisz próbę obejścia: samodzielny wire packet, nieaktualny context, NaN/Inf, oś poza zakresem albo niedozwolony vertical. Wskaż dokładną gałąź odrzucenia; nie uruchamiaj tych scenariuszy.
