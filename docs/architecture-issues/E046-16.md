## Instrukcja wykonania krok po kroku

1. Zbierz raporty issues 01–15 i rozbij kryteria oryginalnych kroków 01–45 na wiersze: wymaganie, właściciel, symbol/plik, consumer, dowód przeglądu, nierozstrzygnięte ryzyko. Brak dowodu wraca do odpowiedniego issue przed otwarciem kompilacji.

2. Popraw architecture.toml i docs/architecture.md tak, by nazwy pakietów/odpowiedzialności odpowiadały końcowemu kodowi; usuń planned wpisy już wykonanych pakietów i nie twórz pustych crate.

3. W docs/protocol i dokumentacji zapisu opisz wyłącznie 18/10 oraz generator 5, rejection starych danych i potrzebę osobnego katalogu. Dopisz dokładne semantyki seq/ack/revision, full/delta i content_initialized ustalone w implementacji.

4. Opisz trzy przepływy z nazwami rzeczywistych API: authentication→Principal→permission; intent→policy→tick→ack→replay; entity effect→budget→commit→save/journal→replica. Uwzględnij błędy i anulowanie na granicach.

5. W README właściwych pakietów dodaj instrukcje nowej domeny loggera, komunikatu Fluent, input action i modułu sample. Każdy przykład wskazuje istniejącego konsumenta; nie pokazuj hipotetycznego API.

6. Zaktualizuj architecture-execution i epic: osobno source complete, compiled, runtime unverified. Nie oznaczaj final done przed E046-17/18. Usuń sprzeczności z historycznymi Complete i zapisz brak kont/TLS oraz brak wizualnego potwierdzenia cieni.
